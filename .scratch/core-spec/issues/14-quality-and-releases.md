# Качество и релизы: общая проверка, тест-нарушение, CI и release-please

Type: grilling
Status: resolved
Blocked by: 12, 13

## Question

Что входит в общую команду проверок? Каким должен быть тест с намеренным нарушением правила записи (какое правило нарушается и как доказывается, что проверки его ловят: постоянный тест или отдельный шаг в CI)? Какие workflow нужны в GitHub Actions и как настраивается release-please?

## Текущее состояние

`mise run check` (TypeSpec, SDK, тесты, Oxlint, сборка) запускается в `project-check`; намеренное нарушение один раз проверялось вручную (без блокировки тест на гонку падает); release-please нет.

## Answer

Решено 2026-11-23 без отдельных вопросов: выбрана простая схема для одного учебного репозитория с учётом исследования release-please и ограничения `GITHUB_TOKEN`.

### Проверка сгенерированных файлов (уточнение тикета «Design First»)

`git diff --exit-code` не видит новые неотслеживаемые файлы, а генератор SDK не удаляет устаревшие. Поэтому:

1. Перед генерацией SDK каталог `frontend/src/shared/api/generated/` очищается, кроме `.openapi-generator-ignore`: удалённые из контракта модели исчезают и проявляются как удалённые файлы.
2. После генерации проверка — `git status --porcelain -- contracts/openapi frontend/src/shared/api/generated`; непустой вывод (изменённые, удалённые и неотслеживаемые файлы) валит `check` с подсказкой выполнить `mise run generate` и закоммитить результат.
   - Уточнено при реализации (тикет [Реализация](15-vertical-slices.md)): проверка выполняется только в CI (`CI=true`), локально пропускается — иначе `check` падал бы при любой незакоммиченной правке контракта.
3. `.gitattributes` с `text eol=lf` для этих путей (тикет «Design First») исключает ложные срабатывания из-за CRLF на Windows.

### Общая команда проверок

`mise run check` по порядку: генерация (TypeSpec → OpenAPI → SDK → серверные интерфейсы) → проверка сгенерированных файлов → тесты бэкенда (модульные, интеграционные, прямые HTTP) → тесты фронтенда → Oxlint → сборка фронтенда. Браузерный сценарий — отдельно, `mise run e2e` (нужны браузеры Playwright).

### Тест с намеренным нарушением правила записи

Постоянные негативные тесты в интеграционном наборе бэкенда (входят в `check` и CI), каждый намеренно пытается нарушить правило и ожидает отказ 409 «слот недоступен» и неизменный список записей:

- одновременные запросы на одно и то же время — успешна ровно одна запись (ADR-0002);
- запись другого типа встречи, пересекающаяся с существующей (общая занятость);
- запись вне окна записи и вне сетки слотов.

Тест одновременных запросов обязан падать, если убрать блокировку (так он уже проверялся вручную); отдельный «мутационный» шаг в CI не вводится.

### GitHub Actions

- `project-check.yml` (существующий): задача `check` — установка инструментов mise, `npm ci` для `contracts`, `frontend` (и `e2e`), `mise run check`; новая задача `e2e` после неё — установка Chromium для Playwright с зависимостями и `mise run e2e`.
- `hexlet-check.yml` не меняется.
- `release-please.yml` (новый), ниже.

### Релизы: release-please

- `googleapis/release-please-action@v5`, триггер — `push` в `master`; `permissions: contents: write, pull-requests: write, issues: write`; токен — стандартный `GITHUB_TOKEN`, без PAT и секретов.
- Manifest-режим, один корневой пакет `"."`, `release-type: simple`: одна версия репозитория в `version.txt`, общий `CHANGELOG.md`, тег `vX.Y.Z`; `bump-minor-pre-major: true`; первая версия `0.1.0`. Версии в `pom.xml` и `package.json` release-please не трогает: ничего не публикуется, эти поля не используются.
- Процесс: каждый push в `master` создаёт или обновляет release PR; релиз и тег появляются, когда владелец сливает этот PR.
- Ограничение `GITHUB_TOKEN` принимается осознанно: release PR и тег не запускают `project-check` и `hexlet-check`. Это безопасно: release PR меняет только `version.txt` и `CHANGELOG.md`, а слияние PR — обычный push в `master`, на котором обе проверки запускаются как всегда.
- Ручной шаг владельца репозитория: включить Settings → Actions → General → «Allow GitHub Actions to create and approve pull requests».

Расхождения с текущей реализацией: проверка сгенерированных файлов и очистка каталога SDK отсутствуют; нет задачи `e2e` в CI и `mise run e2e`; нет `release-please.yml`, `version.txt`, `CHANGELOG.md` и конфигурации release-please; негативные тесты на окно и сетку отсутствуют (тест гонки и пересечения есть). `mise run check` и `project-check.yml` существуют, но без новых шагов.

Открытые вопросы: нет. Словарь не менялся.
