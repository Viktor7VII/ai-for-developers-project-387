# Один владелец без входа в систему

В первой версии в системе ровно один владелец, а его кабинет (`/admin`, API под `/api/` вне `/api/public/`) открыт без авторизации. Мы сознательно отказались от регистрации, входа и разделения данных по владельцам, чтобы быстрее довести до работы основной сценарий «тип встречи → расписание → запись гостя». Это не уязвимость по недосмотру: приложение рассчитано на локальный запуск и учебную демонстрацию.

## Consequences

- В модели данных нет сущности владельца: типы встреч, расписание и записи принадлежат ему неявно, а расписание хранится в единственной строке.
- Занятость общая для всех типов встреч: запись любого типа занимает время владельца целиком.
- Главная страница гостя берёт список типов встреч из API кабинета (`GET /api/event-types`), а не из отдельного публичного эндпоинта: пока кабинет открыт, отдельный эндпоинт ничего не даёт. При добавлении авторизации этот список нужно вынести в публичный API, иначе главная перестанет работать.
- Перед публичным развёртыванием нужно добавить авторизацию владельца. Это потребует владельца в модели данных и разделения API кабинета и публичного API, которое уже заложено префиксом `/api/public/`.
