## О проекте

Сервис позволит владельцу создавать типы встреч, настраивать доступное время и предоставлять гостям ссылку для самостоятельной записи.

Основной референс проекта — [Cal.com](https://cal.com/). При изучении сервиса я рассмотрел основной сценарий: от создания типа встречи до появления новой записи в списке владельца.

## Пользовательский сценарий

1. **Создание типа встречи.** Владелец заходит в личный кабинет, открывает раздел типов встреч и создаёт новый тип встречи. Указывает название, описание и продолжительность, например «Консультация» на 30 минут. После сохранения для него формируется ссылка для записи.

2. **Настройка расписания.** Владелец задаёт дни и часы, когда готов проводить встречи. Например, с понедельника по пятницу с 09:00 до 17:00. На основании расписания система определяет доступные даты и время.

3. **Публикация ссылки.** Владелец копирует ссылку на созданный тип встречи и отправляет её гостю.

4. **Выбор времени.** Гость открывает ссылку без регистрации, видит информацию о типе встречи, выбирает доступную дату и свободный слот.

5. **Заполнение данных.** Гость указывает своё имя и email, проверяет информацию о типе встречи и подтверждает запись.

6. **Создание записи.** Система повторно проверяет доступность выбранного времени и создаёт запись, если слот свободен. Записи присваивается статус подтверждённой.

7. **Просмотр записи владельцем.** В личном кабинете владельца, в разделе записей, появляется новая запись. Владелец видит название типа встречи, имя и email гостя, дату, время и статус записи.

Таким образом, основной сценарий выглядит следующим образом:

**Создание типа встречи → настройка расписания → отправка ссылки → выбор свободного времени → заполнение формы → подтверждение записи → просмотр записи владельцем.**

## Основные правила работы

- Один владелец может создавать несколько типов встреч.
- Для каждого типа встречи задаётся своя продолжительность.
- Гость может записаться без регистрации.
- Доступное время формируется на основании расписания владельца.
- Уже занятое время не должно предлагаться другим гостям.
- Перед созданием записи система должна повторно проверить доступность выбранного времени.
- Созданная запись появляется в списке записей владельца.
- Изменение расписания не должно менять уже созданные записи.

## Стек

- Backend: Java, Spring Boot.
- Frontend: TypeScript, React, Vite.
- UI: Mantine.
- API: TypeSpec → OpenAPI → сгенерированный TypeScript-клиент.
- База данных: H2 (встроенная, хранится в файле). Переход на PostgreSQL запланирован.
- Сборка backend: Maven.
- Тестирование: JUnit 5, Vitest, Testing Library.
- Линтер frontend: Oxlint.
- Управление инструментами и задачами: mise.
- CI: GitHub Actions.

## Установка

Клонирование репозитория:

```bash
git clone https://github.com/Viktor7VII/ai-for-developers-project-387.git
cd ai-for-developers-project-387
```

Версии Java, Maven и Node.js закреплены в `mise.toml`. Установка инструментов и git-хука для проверки сообщений коммитов:

```bash
mise install
mise exec -- hk install
```

Установка зависимостей:

```bash
cd backend && ./mvnw dependency:resolve && cd ..
cd contracts && npm install && cd ..
cd frontend && npm install && cd ..
```

На Windows в PowerShell используйте `.\mvnw.cmd` вместо `./mvnw` и `npm.cmd` вместо `npm`.

## Запуск

Приложение состоит из двух частей, их нужно запустить в отдельных терминалах.

Backend (http://localhost:8080):

```bash
cd backend
./mvnw spring-boot:run
```

Frontend (http://localhost:5173):

```bash
cd frontend
npm run dev
```

Dev-сервер Vite проксирует запросы `/api` на backend. Если backend запущен на другом адресе, укажите его в переменной окружения `BACKEND_URL`.

Данные хранятся в файле `backend/data/calendar.mv.db` и сохраняются между перезапусками. Чтобы начать с чистой базы, остановите backend и удалите папку `backend/data`.

## Использование

Главная страница http://localhost:5173 предназначена для гостя: на ней перечислены типы встреч, кнопка «Записаться» ведёт на страницу записи. Ссылка «Кабинет владельца» в шапке ведёт в кабинет.

Кабинет владельца открывается по адресу http://localhost:5173/admin (регистрации нет, владелец один, см. [ADR-0001](docs/adr/0001-single-owner-without-authentication.md)):

1. **Типы встреч** — создайте тип встречи: название, ссылка, описание и длительность. Кнопка «Скопировать ссылку» копирует адрес публичной страницы записи.
2. **Расписание** — укажите часовой пояс, рабочие дни и интервалы времени. По умолчанию: понедельник–пятница, 09:00–17:00, UTC.
3. **Записи** — список предстоящих и прошедших записей с именем и email гостя.

Гость открывает главную или ссылку для записи вида http://localhost:5173/book/konsultatsiya, выбирает дату и свободный слот, вводит имя и email и подтверждает запись. Время показывается в часовом поясе гостя.

### API

| Метод | Путь | Назначение |
|---|---|---|
| `GET`, `POST` | `/api/event-types` | Список и создание типов встреч |
| `GET`, `PUT`, `DELETE` | `/api/event-types/{id}` | Получение, изменение и удаление типа встречи (удаление — только без записей) |
| `GET`, `PUT` | `/api/schedule` | Расписание владельца |
| `GET` | `/api/bookings` | Записи владельца |
| `GET` | `/api/public/event-types/{slug}` | Информация о типе встречи для гостя |
| `GET` | `/api/public/event-types/{slug}/slots` | Свободные слоты окна записи: сегодня и 13 следующих дней по времени владельца (время в UTC) |
| `POST` | `/api/public/event-types/{slug}/bookings` | Создание записи |

Полное описание — в контракте `contracts/main.tsp` и сгенерированной спецификации `contracts/openapi/openapi.yaml`.

## Проверки

Все проверки проекта (компиляция контракта, генерация SDK, тесты лимита запусков агента, тесты backend и frontend, линтер, сборка) запускаются одной командой из корня репозитория:

```bash
mise run check
```

Эта же команда выполняется в CI на каждый push.

Браузерный сценарий (Playwright, пакет `e2e/`) проходит основной путь на настоящих серверах: владелец создаёт тип встречи и расписание, гость записывается с главной, владелец видит запись. Серверы поднимаются автоматически (бэкенд на порту 18080 с временной базой, фронтенд на 15173). Перед первым запуском установите браузер командой `npx playwright install chromium` в каталоге `e2e`:

```bash
mise run e2e
```

В CI сценарий выполняется отдельной задачей `e2e` после общей проверки.

## Docker и деплой

Приложение собирается в один Docker-образ: бэкенд отдаёт и API, и собранный фронтенд на порту из переменной окружения `PORT` (по умолчанию 8080).

```bash
docker build -t call-calendar .
docker run -p 8080:8080 -e PORT=8080 call-calendar
```

Публичная версия (развёрнута из первого проекта): https://call-calendar-gvm0.onrender.com (Render, Docker web service, бесплатный тариф: после простоя первый запрос может идти до минуты, пока сервис «просыпается»). Кабинет владельца — https://call-calendar-gvm0.onrender.com/admin.

### Хранение данных

База — встроенная H2 в файле `/app/data/calendar.mv.db` внутри контейнера.

- На бесплатном тарифе Render файловая система контейнера временная: при перезапуске, повторном деплое или «засыпании» сервиса данные сбрасываются к пустой базе.
- Чтобы данные сохранялись после перезапуска, к сервису подключается постоянный диск (Render Disk, платные тарифы) с точкой монтирования `/app/data`; при локальном запуске — том: `docker run -v call-calendar-data:/app/data …`.

### Render MCP

В репозитории лежит `.mcp.json` с подключением к Render MCP (`https://mcp.render.com/mcp`). Ключ в Git не хранится: заголовок авторизации берётся из переменной окружения `RENDER_API_KEY`.

1. Создайте API-ключ в Render: Account Settings → API Keys.
2. Задайте переменную окружения `RENDER_API_KEY` в своей системе (не в файлах репозитория).
3. Перезапустите Claude Code в каталоге проекта и разрешите сервер `render` из `.mcp.json`.

## Работа с GitHub Agent

В репозитории настроен агент [OpenCode](https://opencode.ai/docs/github/) (workflow `.github/workflows/opencode.yml`). Он запускается в GitHub Actions по комментарию с командой `/oc` или `/opencode`:

- в issue — например, `/oc объясни эту задачу` или `/opencode предложи исправление`; агент отвечает комментарием или открывает Pull Request с изменениями;
- в Pull Request — общий комментарий или комментарий к строкам кода на вкладке Files changed, например `/oc добавь обработку ошибок здесь`.

Правила запуска:

- Команда пишется отдельным словом; после неё можно ставить знак препинания (`/oc, исправь тест`). Команды внутри цитат, блоков кода, `<pre>` и HTML-комментариев не учитываются.
- Агент вызывается только комментарием в GitHub (в issue или Pull Request); в локальном терминале или IDE `/oc` агента не запускает.
- Агента может вызвать только владелец репозитория; комментарии ботов игнорируются.
- Pull Request из форков агент не обрабатывает.
- Агент читает `AGENTS.md` и скиллы из `.claude/skills/`. По issue он создаёт отдельную ветку, в Pull Request коммитит в его ветку; в `main` изменения попадают только через Pull Request (ветка защищена).

Для работы на репозиторий должно быть установлено приложение [OpenCode GitHub App](https://github.com/apps/opencode-agent). По умолчанию используется бесплатная модель `opencode/deepseek-v4.1-flash-free`, API-ключи не нужны; другую модель можно задать переменной репозитория `OPENCODE_MODEL` (Settings → Secrets and variables → Actions → Variables).

### Авторевью Pull Request

Workflow `.github/workflows/opencode-review.yml` автоматически проверяет Pull Request в `main` по критериям [REVIEW.md](REVIEW.md) и публикует ревью комментарием.

- Запускается при открытии, новом push, переоткрытии и выходе из черновика — для PR владельца репозитория и PR самого агента (`opencode-agent[bot]`) из веток этого репозитория. Черновики, форки и PR release-please не проверяются.
- В задание ревьюеру передаются `REVIEW.md`, описание PR, diff и связанные Issues из описания и коммитов (тикет, спецификация, исходное обращение) вместе с комментариями владельца — подтверждением требований человеком. Отсутствие связанного Issue или подтверждения ревью отмечает первым замечанием.
- Ревью независимое и только для чтения: отдельный запуск `opencode run` (OpenCode CLI 2.4.1) без токенов и секретов; агенту разрешено только чтение файлов PR (правка, команды, сеть и файлы вне репозитория запрещены), checkout без сохранённых учётных данных, после ревью проверяется, что файлы не изменены. Исправления вносит человек или агент по команде `/oc` владельца — авторевью код не меняет и PR не одобряет.
- Новый push отменяет незавершённое ревью предыдущего коммита; `opencode run` ограничен 12 минутами, тайм-аут job — 20 минут.
- Исчерпанная дневная квота бесплатной модели определяется самим запуском ревью без отдельного пробного запроса: OpenCode Zen отклоняет такой запрос до работы модели, OpenCode 2.x не повторяет его, и запуск за секунды завершается ошибкой «Free model quota exhausted» и не расходует лимит PR.
- OpenCode GitHub Action здесь не используется: он отклоняет события, вызванные его собственным ботом, поэтому не может проверять PR агента.

### Лимит запусков агента

На один Pull Request — не больше трёх запусков агента: авторевью и команды `/oc` считаются вместе (в issue лимита нет).

- Лимит проверяется внутри job, которая вызывает модель, до вызова модели, поэтому повторный запуск (Re-run) проверяется заново и тоже расходует запуск.
- Бюджет считается по истории GitHub Actions обоих workflow (job с выполненным шагом «Reserve agent run»), а не по комментарию: агент не может его изменить или сбросить — у приложения OpenCode только чтение Actions. Job упорядочены по id: каждая учитывает все более ранние, ещё не завершённые — с запасом. Actions API показывает новые запуски с задержкой, поэтому список запусков читается без поисковых фильтров, а лимит проверяется дважды с паузой 20 секунд, оба раза до вызова модели. Полной атомарности API GitHub не даёт: лимит может быть превышен, если API покажет более ранний запуск позже этой паузы или если раннер авторевью пропадёт после вызова модели, но до шага резервирования. Этот остаточный риск принят сознательно, см. [ADR-0004](docs/adr/0004-agent-run-limit-from-actions-history.md).
- Запуск `/oc` засчитывается перед вызовом агента, авторевью — после попытки ревью, в том числе если она отменена новым push, превысила время или завершилась ошибкой модели; не засчитывается только авторевью, отклонённое из-за исчерпанной квоты бесплатной модели. Пока ревью выполняется, лимит учитывает его как занятый запуск. Отклонённый лимитом запуск завершается ошибкой, а комментарий `github-actions[bot]` в PR сообщает об исчерпании лимита; сбросить лимит нельзя.
- Команды `/oc` одного PR не теряются и выполняются по очереди в порядке поступления: каждая ждёт завершения предыдущих (GitHub concurrency для них не используется — он отбрасывает ожидающие запуски).

Ограничения: бесплатная модель ограничена по частоте запросов на IP раннера и может отвечать ошибкой `429`; качество ревью зависит от модели — оно не заменяет проверку человеком и `mise run check`.

## Релизы

Версии выпускаются через [release-please](https://github.com/googleapis/release-please): одна версия на весь репозиторий (`version.txt`), общий `CHANGELOG.md` и теги `vX.Y.Z`, первая версия — 0.1.0. После каждого push в `main` workflow `release-please` открывает или обновляет release PR со списком изменений из Conventional Commits; релиз и тег создаются, когда этот PR сливают. Для работы в настройках репозитория должно быть включено Settings → Actions → General → «Allow GitHub Actions to create and approve pull requests».
