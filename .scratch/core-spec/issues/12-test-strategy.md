# Проверка приложения: уровни тестов и браузерный сценарий

Type: grilling
Status: resolved
Blocked by: 07, 09

## Question

Что проверяется на каждом уровне: модульные тесты (правила слотов и конфликтов), интеграционные (API с базой), прямые запросы к API, браузерный сценарий с настоящим сервером? Каким инструментом и в каком окружении (локально, CI) запускается браузерный сценарий и какой путь пользователя он проходит?

## Текущее состояние

JUnit + MockMvc на бэкенде (51 тест), Vitest + Testing Library с подменённым API на фронтенде; браузерных тестов и тестов с настоящим сервером нет.

## Answer

Решено 2026-11-23 без отдельных вопросов: продуктовых развилок нет; уровни и сценарии выводятся из спецификации (тикеты 01–09, ADR-0001, ADR-0002).

### Уровни

1. **Модульные тесты бэкенда (JUnit, без Spring и базы).** Чистая логика слотов и окна: шаг = длительность, сетка от начала интервала, остаток отбрасывается, примыкающие интервалы не склеиваются; окно записи (сегодня + 13 дней в поясе владельца, граница 00:00 пятнадцатого дня, по началу слота, исключение начавшихся); часовые поясы и переходы на летнее время; исключение слотов по пересечению с записями при полуоткрытых интервалах и разрешённом примыкании. «Сейчас» — фиксированный момент.
2. **Интеграционные тесты бэкенда (Spring Boot + H2 в памяти, MockMvc, фиксированные часы).** Каждая операция API из тикета «API-контракт: эндпоинты»: успешный ответ и каждый случай ошибки (400 / 404 / 409) с форматом `{ message }`. Правила записи на сервере: окно, сетка, общая занятость разных типов, примыкание, удаление типа с записями и без, записи вне изменённого расписания. Тест одновременных запросов: N потоков создают запись на одно и то же или пересекающееся время — успешна ровно одна; без блокировки тест падает (ADR-0002).
3. **Прямые HTTP-запросы к API (Spring Boot на случайном порту, настоящий HTTP и JSON).** Сквозной сценарий через сеть без браузера: создать тип встречи → получить слоты по ссылке для записи → создать запись → увидеть её в списке записей → повторная запись на то же время даёт 409. Проверяет сериализацию времени (UTC ISO 8601), коды и заголовки так, как их видит клиент.
4. **Тесты фронтенда (Vitest + Testing Library, API-клиент подменён).** Поведение страниц на уровне маршрутов: главная, страница записи (выбор дня и слота, форма гостя, подтверждение, «слот недоступен» → перезагрузка слотов), кабинет (типы встреч с удалением, расписание с IANA-поясами, записи).
5. **Браузерный сценарий с настоящим сервером (Playwright).** Один сквозной сценарий основного пути из README на реально запущенных бэкенде и фронтенде: владелец создаёт тип встречи и задаёт расписание (все дни, широкий интервал, пояс UTC — чтобы слоты были в любой день и час запуска) → гость открывает главную, переходит по «Записаться», выбирает первый свободный слот, вводит имя и email, видит подтверждение → владелец видит запись в кабинете. Бэкенд запускается с временной базой H2 (через `CALENDAR_DB_URL`), фронтенд — через Vite с прокси на бэкенд; Playwright поднимает оба сервера сам.

### Размещение и запуск

- Уровни 1–3 — в `backend/src/test`, уровень 4 — в `frontend/src`; все входят в `mise run check`.
- Браузерный сценарий — отдельный пакет `e2e/` в корне репозитория (Playwright и его зависимости не попадают во фронтенд) с отдельной командой `mise run e2e`. Входит ли он в общую проверку и в GitHub Actions — решает тикет «Качество и релизы».
- Новая зависимость — Playwright; причина — требование браузерного сценария с настоящим сервером.

Расхождения с текущей реализацией: нет уровня 3 (прямые HTTP-запросы, кроме теста health), нет браузерного сценария и пакета `e2e/`; нет тестов на окно записи, удаление типа встречи и отклонение не-IANA поясов (этих функций пока нет). Модульные, интеграционные и фронтенд-тесты на остальное уже есть, включая тест одновременных запросов.

Открытые вопросы: нет. Словарь не менялся.
