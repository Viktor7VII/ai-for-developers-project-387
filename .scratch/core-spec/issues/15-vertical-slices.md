# Реализация: вертикальные тикеты и первая сквозная функция

Type: grilling
Status: resolved
Blocked by: 09, 11, 12

## Question

Какая функция станет первой сквозной через всю контрактную цепочку (TypeSpec → генерация → бэкенд → фронтенд → тесты)? По какому принципу спецификация режется на вертикальные тикеты и какие между ними зависимости?

## Текущее состояние

Функциональность реализована без вертикальной декомпозиции; новая спецификация может потребовать доработки существующего кода.

## Answer

Решено 2026-11-23; первый срез реализован (не закоммичен, ветка `feat/event-type-delete`).

### Принцип нарезки

Каждый вертикальный тикет — одно наблюдаемое поведение через всю цепочку: контракт TypeSpec → генерация (OpenAPI, серверные интерфейсы и DTO, TS SDK) → бэкенд → фронтенд → тесты на уровнях из тикета «Проверка приложения». Ресурс переводится на сгенерированные интерфейсы в том срезе, который первым меняет его поведение.

### Срезы и зависимости

1. **Удаление типа встречи + цепочка генерации** — реализован: `DELETE /api/event-types/{id}` (204, 404, 409 при наличии записей), отдельная входная модель `EventTypeInput` (в запросах нет `id`, непустое название проверяется контрактом), контроллер типов встреч реализует сгенерированный `EventTypesApi`, ошибки — сгенерированный `ErrorResponse`, публичная страница типа встречи отдаёт сгенерированную модель; плагин OpenAPI Generator 7.27.0 в Maven, `mise run generate`, очистка каталога SDK, проверка сгенерированных файлов, `.gitattributes`; кнопка «Удалить» с подтверждением в кабинете; тесты бэкенда и фронтенда; AGENTS.md.
2. **Расписание на сгенерированных интерфейсах + только IANA** — зависит от 1.
3. **Окно записи:** слоты без параметров, проверка окна при записи, публичный API и записи кабинета на сгенерированных интерфейсах, страница записи под новый API — зависит от 1.
4. **Негативные тесты нарушения правил записи (окно, сетка) и прямые HTTP-тесты основного сценария** — зависит от 3.
5. **Браузерный сценарий Playwright** (`e2e/`, `mise run e2e`, задача `e2e` в CI) — зависит от 3.
6. **release-please** (workflow, конфигурация, `version.txt`, ручная настройка репозитория) — независим.

### Уточнение по реальному противоречию

Проверка сгенерированных файлов (`git status --porcelain`) запускается только в CI (`CI=true`, его выставляет GitHub Actions): локально она падала бы при любой незакоммиченной правке контракта, а AGENTS.md требует запускать `mise run check` до коммита. Локально выводится сообщение о пропуске. Уточнение внесено в тикет «Качество и релизы».

### Проверки первого среза

- `mise run check` локально: зелёный (бэкенд 54 теста, фронтенд 34 теста, Oxlint, сборка).
- `CI=1 node scripts/check.mjs`: проверка сгенерированных файлов падает до тестов и показывает новые неотслеживаемые файлы `EventTypeInput.*` — ожидаемо, пока изменения не закоммичены.

Открытые вопросы: нет. Словарь не менялся.
