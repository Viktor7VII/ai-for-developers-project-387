# Лимит запусков агента — по истории GitHub Actions с повторной проверкой

Лимит в три запуска агента на Pull Request (авторевью и команды `/oc` вместе) считается по истории GitHub Actions обоих workflow: каждая job агента до вызова модели учитывает все более ранние по id job агентов этого PR, которые заняли запуск (выполнен шаг «Reserve agent run») или ещё могут его занять. Историю Actions агент изменить не может — у приложения OpenCode только чтение Actions. Поскольку Actions API не гарантирует, что только что созданный запуск сразу виден, список запусков читается без поисковых фильтров, а лимит проверяется дважды с паузой 20 секунд, оба раза до вызова модели и до резервирования.

Мы сознательно приняли остаточный риск: лимит может быть превышен, если API покажет более раннюю job позже этой паузы, или если раннер авторевью пропадёт после вызова модели, но до шага резервирования. Для учебного репозитория с одним доверенным автором и бесплатной моделью последствие — один лишний бесплатный запуск, а полная атомарность потребовала бы дополнительных прав и настроек.

## Considered Options

- Атомарные слоты на Git refs (`refs/tags/agent-run/pr-<N>/slot-<k>`, создание ref завершается ошибкой, если слот занят) с тегами-возвратами для исчерпанной квоты — исключает гонку, но требует ruleset тегов с запретом удаления и изменения, `contents: write` для job резервирования, двух дополнительных job в обоих workflow и накапливает теги в репозитории.
- Счётчик в комментарии PR — агент может удалить комментарий и сбросить бюджет (у приложения OpenCode есть `issues: write`).
- GitHub concurrency как очередь — заменяет ожидающий запуск следующим, и команды `/oc` теряются.
